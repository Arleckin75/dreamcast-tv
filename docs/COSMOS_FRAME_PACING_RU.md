# Повторная проверка плавности на Cosmos

> Уточнение методики: в старом сборщике гистограмм SurfaceFlinger могла выбираться
> уже закрытая поверхность с повторяющимся именем. Приведённые ниже прежние доли
> интервалов предварительные; использовать их как доказательство эффективности
> изменений нельзя. Счётчики декодера, временные метки кадров и CPU от этой ошибки
> не зависят. Для повторных проверок каждому окну присваивается уникальная метка,
> а тест требует единственную соответствующую ей поверхность.

Дата: 06.11.2026. Проверялось AV1 1280×720, скорость 1×, качество «Авто».
Входной формат сообщает 24,39 кадра/с; экран Cosmos работает на 50 Гц.
Замеры выполнены через ADB и отдельный пакет `.cosmosperf` без замены
установленного приложения и его данных.

## Наблюдения

- В текущем приложении один запуск потерял 61 кадр за первые 4,3 секунды,
  затем ещё 8 за следующие 13 секунд. Другой запуск не показал такой серии
  пропусков. Это не основание объявлять проблему полностью устранённой.
- При повторных сравнительных замерах одной сцены, с позиции 130 секунд,
  потери составляли 0–1 кадр за 30 секунд. Запас видео в буфере — около
  50 секунд; недостаток сети в этих измерениях не наблюдался.
- SurfaceFlinger показывает неравномерные интервалы вывода: примерно 20,
  40 и 60 мс, иногда больше. Нулевой счётчик пропусков у декодера сам по себе
  не доказывает равномерный показ кадров на экране.
- При видео около 24 кадров/с и экране 50 Гц равные интервалы невозможны.
  Однако наблюдаемые короткие интервалы около 20 мс с последующими длинными
  интервалами требуют отдельного исследования; объяснять всё только частотой
  экрана по этим данным нельзя.

## Проверенные эксперименты

Оба эксперимента сравнивались с текущей очередью dav1d на 12 буферов.
Каждый вариант запускался дважды по 30 секунд на одном участке видео.

| Вариант | Пропущено кадров, два запуска | Интервалы около 19–20 мс, два запуска |
| --- | --- | --- |
| Обычный GL, сравнение с отложенной передачей | 0 / 0 | 136 / 122 |
| Отложенная передача с VideoFrameReleaseHelper | 0 / 0 | 124 / 110 |
| Обычный GL, сравнение с метками EGL | 1 / 0 | 152 / 128 |
| Передача времени показа через EGL | 1 / 0 | 137 / 101 |

Небольшое изменение распределения не подтверждает устойчивого улучшения
плавности: между повторами меняется и контрольный результат, длинные интервалы
сохраняются. Экспериментальные рендереры удалены из приложения.
Увеличенная очередь dav1d и снижение качества «Авто» при устойчивой потере
кадров сохранены. Аппаратное декодирование не менялось.

## Сравнение 720p и 480p

Дополнительно выполнено по три 30-секундных замера с очередями на 12 буферов.
Порядок: 720, 480, 480, 720, 720, 480. Каждый запуск начинается с позиции
120 секунд; после прогрева до 130 секунд измеряется один и тот же участок
до примерно 160 секунд. Счётчики кадров берутся как разница за измеряемое окно.
Проверяется, что выбранное разрешение действительно используется.

| Показатель | 720p | 480p |
| --- | --- | --- |
| Средняя загрузка процесса | около 160% | около 84% |
| Пропущенные кадры за три замера | 0 / 0 / 0 | 0 / 0 / 0 |
| Доля интервалов около 19–20 мс | 15,8–19,1% | 14,9–17,5% |
| Интервалы около 80 мс и больше | 3 / 4 / 6 | 2 / 0 / 2 |

Загрузка вычисляется из процессорного времени процесса приложения за окно:
100% соответствует одному полностью занятому ядру. Это нагрузка всего
тестового приложения, а не только потоков dav1d.

480p почти вдвое снижает нагрузку и уменьшает число длинных задержек в этих
замерах, но короткие интервалы сохраняются, а диапазоны их долей перекрываются.
Это не подтверждает устранение оставшейся неравномерности снижением разрешения.
Принудительный предел «Авто» до 480p не введён; сохранён предел до 720p
со снижением при устойчивых пропусках кадров.

Отдельно проверяются разности временных меток кадров перед передачей в GL.
Для обоих разрешений на этом участке они равны 41 и 42 мс — в среднем примерно 24 кадра/с,
несмотря на оценку 24,39 в `Format.frameRate`. Следовательно, интервалы около
20 мс в SurfaceFlinger не объясняются такими интервалами исходных временных
меток. В дополнительной паре замеров с записью этих меток оба разрешения дали
по 109 коротких интервалов показа и ноль пропущенных кадров.
Следующее направление исследования — путь вывода кадра и его
синхронизация с компоновщиком экрана. Эти измерения относятся к одной сцене
и не исключают перегрузку декодера на других видео или при другой нагрузке ТВ.

## Повторение диагностики

`Dav1dPerformanceTest` запускается только с явно переданными параметрами
`performanceReleaseId`, `performanceReleaseUrl` и `performanceEpisodeId`.
Используйте отдельный пакет через `-PnativeDebugSuffix=.cosmosperf`.
Во время замера не переключайте приложение и не нажимайте кнопки пульта.

Тест сравнивает стандартные очереди Media3 с увеличенными очередями dav1d,
собирает счётчики декодера и гистограмму `present2present` SurfaceFlinger
для SurfaceView тестового пакета. Результаты находятся в журнале `DCTV_BENCH`.
Для сравнения качества передайте
`-Pandroid.testInstrumentationRunnerArguments.performanceCompareQuality=true`.
По умолчанию выполняются шесть замеров в указанном выше порядке; параметр
`performanceHeights=720,480` позволяет выбрать короткое сравнение.
Тест также записывает процессорное время и разности временных меток кадров.
Аргументы зависят от выбранной серии; тест не содержит адресов подписанных
видеопотоков и не использует пользовательское хранилище установленного APK.
