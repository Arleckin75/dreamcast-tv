# Dream Cast TV v0.7.1 — безопасная схема публикации

## Что изменяет патч
- Удаляет ввод `source_branch`: workflow всегда использует commit выбранной ветки (`github.sha`).
- Ветка `develop` может собирать **только Debug**. Подпись `release-signing` и публикация требуют **ветку `main`**.
- Сохраняет оба flavor: `software_AV1` (LibVLC) и `hardware_AV1` (ExoPlayer), аудит APK, SHA-256, подпись прежним ключом и сверку сертификата с v0.7.0.
- Удаляет устаревшее задание «Debug v0.7.0 (main)», которое после объединения исходников больше не соответствует main.
- `permissions: contents: read` по умолчанию; право `contents: write` есть только у задания публикации.
- Ничего не меняет в настройках GitHub Environment `release-signing`.

## Порядок действий (требуется сознательная проверка перед публикацией)
1. **В GitHub Desktop выбрать `develop`**. Распаковать ZIP поверх проекта и заменить только `.github/workflows/build-tv-apk.yml`.
2. Commit и Push в `develop`.
3. В GitHub Actions выбрать **Use workflow from: develop**, **Build mode: debug**, запустить; убедиться, что два Debug задания и их аудит успешны.
4. В GitHub создать PR: **base: main ← compare: develop**.
5. Просмотреть *все* изменения PR, особенно `.github/workflows/`, `scripts/`, `android/` и `pubspec.yaml`. Убедиться, что нет доступа к secrets из PR, нет неожиданных команд/зависимостей; проверить статус Debug.
6. После утверждения **Merge PR в main**. Это намеренное обновление стабильной ветки; опубликованная v0.7.0 GitHub Release остаётся доступна.
7. В Actions выбрать **Use workflow from: main**, **Build mode: release**, запустить. Обе Release-сборки должны пройти ABI/engine аудит, проверку подписи и версии. Затем публикация v0.7.1 автоматическая.
8. Проверить GitHub Release: два APK и два SHA-256, затем установку Release поверх v0.7.0 на обоих устройствах.

**Не изменять** ограничения Deployment branches окружения `release-signing`. В нём должна оставаться разрешённой только `main`.

## Важные ограничения
- Патч не создаёт PR и не запускает публикацию автоматически: эти действия нужны в GitHub.
- Инструкция по подписи предполагает, что существующий keystore и его четыре secrets действительно позволяют получить тот же сертификат, что у v0.7.0; workflow проверяет сертификат до публикации.
- Наличие рабочего Debug не гарантирует работоспособность Release; после публикации необходим тест обоих APK на реальных устройствах.
- Если в `main` уже есть существенные изменения относительно `develop`, PR может требовать разрешения конфликтов. Не использовать force-push.
