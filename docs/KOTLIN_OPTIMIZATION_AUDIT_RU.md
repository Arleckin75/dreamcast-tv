# Аудит оптимизации ветки Kotlin

> Исторический отчёт до удаления Dart/Flutter и LibVLC. Актуальная структура сборки описана в [BUILD_TV.md](../BUILD_TV.md).

Дата: 04.11.2026. Исследованный коммит: `ca9dfef`.

Это исходный аудит до изменений. Реализация и результаты проверок: [KOTLIN_OPTIMIZATION_RESULTS_RU.md](KOTLIN_OPTIMIZATION_RESULTS_RU.md).

## Область исследования

Проверены структура ветки и отличие от `main`, нативный модуль `native-android`, оба варианта плеера, общие исходники из `android/app/src/softwareAv1`, модели, парсеры, SQLite/SharedPreferences, кэши, WorkManager, Compose-навигация, тесты, конфигурация Gradle и CI. Сохранённые Flutter-исходники рассмотрены как наследуемая часть и источник совместимости, а не как исполняемый UI нативного приложения. Полный аудит каждой строки Flutter и стороннего VLC в эту проверку не входит.

Ниже подтверждённые свойства кода отделены от предполагаемого эффекта. Замеры производительности на телевизоре не выполнялись. Программный код не изменён: этот документ фиксирует исходное состояние и порядок оптимизации.

## Что уже сделано правильно

- `UiSnapshot` готовится вне главного потока и обновляется по разделам; неизменённые коллекции сохраняют идентичность.
- HTTP отменяется вместе с coroutine; отмена не превращается в успешный ответ из старого кэша.
- `ParsedCache` ограничен 32 записями и суммой длин исходных строк; `FeedCache` — восемью лентами.
- Каталог использует ленивые контейнеры, стабильные ключи, защиту от повторной пагинации; слияние страниц выполняется в `Dispatchers.Default`.
- Анимация масштаба карточки читается внутри `graphicsLayer`; переносить её в отдельную систему анимации ради оптимизации оснований нет.
- Запись прогресса выполняется в фоне через очередь приложения и транзакции; финальная запись переживает уничтожение Activity.
- Software UI ticker уже останавливается при скрытой панели и в `onPause`; общий контроллер не перерисовывает скрытую панель.
- Software использует уменьшенный LibVLC, сборка проверяет состав и размер native-библиотек. Автоматическое удаление дополнительных кодеков без playback-проверки не обосновано.

## Приоритеты

P1 — первый пакет работ; P2 — после него или при подтверждении соответствующего сценария. Приоритет отражает сочетание стоимости и ожидаемой пользы, а не измеренный выигрыш.

### 1. P1: ограничить чтение истории прогресса

`Storage.kt:340,364`, `UiSnapshot.kt:93`, `MainActivity.kt:138,426`.

При каждом `onResume` вызывается `refreshPlayerProgress`. `syncVlcProgress` загружает и сортирует **все** `watch_entries`; затем обновление PROGRESS снова читает все строки, создаёт объекты, группирует их в карты и выбирает десять карточек продолжения. Это выполняется также в hardware-варианте, которому синхронизация VLC не нужна. Индекс для `ORDER BY updated_at DESC,rowid DESC` явно не создаётся; существующая мигрированная БД может иметь дополнительные индексы, поэтому фактический план нужно проверить отдельно.

Предложение: выполнять VLC-синхронизацию только для software; передавать изменённый episode key вместо обхода истории; получать продолжение просмотра отдельным ограниченным запросом, а прогресс серий — по открытому релизу. Добавлять индексы после `EXPLAIN QUERY PLAN` на новой и мигрированной БД. Сохранить нынешнюю семантику: сначала последний эпизод каждого релиза, затем исключение просмотренных.

Проверка: 100 / 1 000 / 10 000 записей; время возврата, длительность SQL и выделения памяти; совместимость старой БД и финальной записи прогресса.

### 2. P1: убрать ненужные hardware-таймеры и одинаковые записи

`HardwarePlayerActivity.kt:58,530,538,597`, `ProgressWriter.kt:28`, `Storage.kt:394`.

`controlTick` работает каждые 500 мс, `saveTick` — каждые 5 с до `onDestroy`. `onStop` только ставит плеер на паузу: callbacks продолжаются. После достижения READY `save()` допускает повторную запись неизменившейся позиции на паузе. Каждая запись меняет две SQL-таблицы и timestamp в preferences. Скрытая панель уже защищена от отрисовки, но опрос состояния остаётся.

Предложение: привязать таймеры к lifecycle и видимости панели, отдельно учесть PiP; периодически сохранять только изменившуюся позицию. Сохранения при seek, завершении, переключении и выходе оставить обязательными. Если объединять очередь, не терять финальный snapshot другого эпизода и порядок `awaitPending`.

Проверка: длительная пауза, Home/возврат, PiP, seek, next episode, смена потока, уничтожение Activity; число записей и callbacks в минуту.

### 3. P1: отменять устаревшее разрешение software-плейлистов

`CosmosFmp4Resolver.kt:15,22,33`, `CosmosAv1PlayerActivity.kt:295`.

Resolver использует глобальный single-thread executor. `requestSerial` отклоняет старый callback, но не останавливает выполняющийся HTTP и не удаляет ожидающие задачи. Новый запрос качества/повторного запуска ждёт завершения предыдущего. У отдельных HTTP connect/read timeout 6/8 с; кандидаты проверяются последовательно.

Предложение: возвращать отменяемую операцию; отменять активный HTTP и ожидающие задачи при новом выборе и выходе. Можно переиспользовать master playlist в рамках одного запуска, сохраняя проверку AV1/fMP4, точного качества и срока подписанных URL. Не добавлять fallback на master.

Проверка: медленный сервер, быстрое переключение качества, Back во время запроса, запуск следующей серии. Новый запрос не должен ждать ненужную предыдущую операцию.

### 4. P1: ограничить рост дискового кэша

`Storage.kt:249,271,282`, `DreamApp.kt:1315`.

TTL проверяется при чтении, но просроченные строки автоматически не удаляются: `clearExpired` вызывается кнопкой настроек. Поиск создаёт ключи для разных запросов и страниц; общего лимита размера/количества нет. Истечение TTL само по себе не освобождает место. `cacheStats` суммирует длины payload всех записей.

Предложение: фоновая очистка с ограничением частоты и объёма, отдельный бюджет дискового кэша. Учитывать режим «навсегда» и договорённость о stale/offline-доступе: немедленное удаление всего просроченного ухудшит существующий fallback. Не запускать тяжёлый VACUUM при каждом старте.

Проверка: тысячи поисковых ключей, объём БД, задержки чтения/записи, сохранение offline-поведения и пользовательских данных.

### 5. P2: сократить повторные чтения и одновременные загрузки repository

`Repository.kt:107,124`, `MainActivity.kt:209`, `HardwarePlayerActivity.kt:177`, `DreamApp.kt:1068`.

`cached` всегда читает исходную строку из SQLite перед обращением в parsed-кэш. Одновременные обращения к одному ключу не объединяются. Данные последовательно проходят Episodes → prepare/playback → hardware load/playback; свежий кэш обычно предотвращает HTTP, но повторные SQL-чтения и переключения диспетчеров остаются. При холодном или принудительном параллельном запросе возможно дублирование HTTP/парсинга.

Предложение: сначала измерить количество чтений на один Play; затем добавить объединение запросов по ключу с корректной отменой отдельного потребителя. Если нужен memory front cache, явно определить TTL, refresh, очистку и invalidation. Не менять двухчасовое обновление подписанных плейлистов.

### 6. P2: показывать stale-данные без ожидания всех retry

`Repository.kt:24,40,132`.

Предыдущий кэш возвращается после неудачи сети. Любая HTTP-ошибка превращается в IOException и повторяется до трёх раз; connect/read timeout — по 45 с, общего call deadline нет. Поэтому существующие данные могут долго не появляться при медленном или ошибочном сервере. Точный максимум не равен простому `3 × 45`: есть несколько фаз соединения и чтения.

Предложение: различать постоянные HTTP-ошибки и временные; задать общий бюджет ожидания. Для каталога/описания рассмотреть немедленный stale-результат с фоновым обновлением. Для подписанных playback URL сохранить отдельную политику свежести. Не применять сетевые изменения без тестов отмены, offline и refresh.

### 7. P2: ограничить объём состояния навигации и лент

`DreamApp.kt:175,202,821`, `FeedCache.kt:6`, `FeedPageMerge.kt:14`.

`SaveableStateHolder` сохраняет состояния разных route keys, но `removeState` не вызывается. Ключи посещённых detail/episodes могут накапливаться в долгой сессии. Число лент ограничено, однако число карточек внутри каждой ленты не ограничено. Каждое слияние страницы заново строит map из всех накопленных карточек: суммарная работа при полной последовательной загрузке растёт квадратично относительно числа страниц фиксированного размера.

Предложение: очищать состояния маршрутов, окончательно удалённых из back stack, сохраняя нужные состояния верхних разделов. Для лент добавить общий бюджет карточек/памяти; при больших каталогах хранить ID-индекс или страницы, чтобы не пересобирать всю ленту. Сначала проверить реальный размер каталога: при небольшом числе страниц эта работа второстепенна.

### 8. P2: уменьшить сканирование SharedPreferences

`Storage.kt:106`, `UiSnapshot.kt:71,83,108`, `EpisodeWorker.kt:25`.

Каждый вызов `records(prefix)` получает `.all` обоих preferences и обходит все ключи. Библиотека, подписки и уведомления делают это отдельно; история уведомлений не ограничена. Снимки UI уже защищают обычный рендер от этих чтений, поэтому проблема проявляется при обновлениях и большой истории, а не на каждом кадре.

Предложение: для одного refresh получать общий снимок preferences один раз; пакетировать связанные изменения одним Editor. При подтверждённом росте вынести коллекции в SQL с сохранением совместимости/миграции; отдельно определить срок хранения уведомлений.

### 9. P2: сократить стоимость фоновых проверок и ожидание CI

`EpisodeWorker.kt:33,45`, `.github/workflows/build-native.yml:20`.

Worker выбирает до 40 подписок. После первой страницы каталога остальные ищутся отдельными последовательными запросами с `refresh=true`; если ни одна подписка не попала в первую страницу, возможно 41 логическое HTTP-обращение до учёта retry. Подписки записываются обратно даже без изменения счётчика. Одноразовая и периодическая работы имеют разные unique names и могут пересекаться.

Предложение: ограниченная конкурентность с небольшим лимитом, общий бюджет времени, запись только изменённых данных и координация двух запусков. Не увеличивать параллелизм без оценки нагрузки на сайт.

В CI hardware-job имеет `needs: libvlc`, хотя скачивание AAR нужно только software. При холодном native-кэше hardware-проверка ждёт сборку чужой зависимости. Разделить hardware и software jobs, сохранив зависимость software от проверенного AAR. Кэширование самого LibVLC уже реализовано.

### 10. P2: проверить release-оптимизацию и добавить нативные метрики

`native-android/app/build.gradle.kts:48`, `DreamApplication.kt:43`, `docs/TV_PERFORMANCE_RU.md`.

В release не включены `isMinifyEnabled`/`isShrinkResources`; baseline profile в нативном модуле не настроен. Это кандидаты для отдельного сравнения размера APK и запуска, а не доказанный источник лагов. Shrinking потребует проверки обоих плееров, JNI, WorkManager и подписанной сборки.

Документ TV_PERFORMANCE описывает в основном Flutter-события. В Kotlin-модуле нет аналогичной сквозной инструментализации startup/catalogue/Play → first rendered frame; сохранён только software output-created marker в общем плеере. Это событие не доказывает вывод первого декодированного кадра. WorkManager вызывается из `Application.onCreate`; перенос его работы имеет смысл только после startup trace.

Предложение: добавить интервалы startup, SQL/cache/parse/network, catalogue ready и первого отображённого кадра для обоих плееров. Снимать frame timings, main-thread trace, PSS/Java/native heap и число обращений к диску. Не записывать URL и поисковые строки.

## Что пока не является основанием для изменений

- `DreamApp.kt` большой, но само число строк не замедляет приложение. Разделение улучшит сопровождение; выигрыш runtime нужно доказывать отдельно.
- `AsyncImage` уже получает ограниченные размеры через layout. По коду нельзя утверждать, что он всегда декодирует оригиналы. Собственный ImageLoader, бюджеты bitmap и prefetch нужны после измерения декодирования, cache hit и памяти.
- Массовое добавление `remember`, аннотаций стабильности и immutable-коллекций без Compose compiler reports может не дать эффекта. Сначала измерить recomposition при D-pad-навигации; не объявлять изменяемые объекты immutable.
- Локальные `Regex` и временные коллекции парсеров — вторичный кандидат после профилирования. Основной unpack уже использует ручной проход вместо дорогих regex word boundaries.
- Сохранённые assets составляют примерно 72 КБ; их удаление не решит проблему памяти видеодекодера.

## Проверки исходного состояния

- Принудительно повторно выполнены `testHardwareAv1DebugUnitTest` и `testSoftwareAv1DebugUnitTest` через task option `--rerun`: **75 + 75 тестов, ошибок и пропусков нет**. Это два варианта одной общей тестовой базы, не 150 уникальных сценариев.
- `lintHardwareAv1Debug` и `lintSoftwareAv1Debug`: BUILD SUCCESSFUL; анализ использовал существующие up-to-date результаты. В отчётах hardware: 0 ошибок, 46 предупреждений; software: 0 ошибок, 51 предупреждение; по 5 hints.
- Instrumentation-тесты, воспроизведение на TV, release APK и измерения до/после в рамках аудита не выполнялись.

## Рекомендуемый порядок реализации

1. Зафиксировать нативные метрики на одной release-сборке и одном устройстве: холодный/тёплый старт, fresh/stale cache, каталог, поиск, возврат из плеера, Play, скрытая панель, пауза и Home.
2. Устранить hardware-таймеры/дубли сохранений и отменять старые software HTTP-операции. Сохранить и проверить lifecycle/PiP/финальный прогресс.
3. Убрать двойное полное чтение истории и ввести управляемую очистку кэша без потери offline-поведения.
4. После замеров — объединение repository-запросов, бюджеты feed/navigation, пакетирование preferences и worker.
5. Отдельно сравнить release с R8/resource shrinking; оптимизацию CI можно выполнить независимо.

Сравнение проводить на одинаковом устройстве, эпизоде, позиции и качестве; для software на слабом ATV начать с 720p. Отчёт должен содержать медиану/P90 с числом повторов, время кадров и память. Ускорение не считать достигнутым только по успешным unit-тестам.
